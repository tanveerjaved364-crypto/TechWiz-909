# Building a trustworthy AI onboarding system: the SkillSprint AI approach

Most onboarding software begins with a deceptively simple question: “What should this new employee learn?” In a real organization, however, the answer is scattered across policies, operating procedures, role descriptions, handbooks, compliance checklists, FAQs, and departmental process guides. It changes with each policy version and it may conflict from one document to another. A system that merely writes attractive training text is therefore not enough. It must be able to prove why a task exists, show the source that supports it, recognize what is mandatory, and stop unsupported material from reaching an employee. SkillSprint AI is designed around that principle.

The application is a fictional Northstar Industries onboarding platform. Its primary goal is to create role-specific learning paths for employees while treating company documentation as the source of truth. It has two intentionally separate pipelines. The first prepares a structured onboarding plan. The second uses ordinary Python rules, not an AI model, to verify the plan. This separation matters because a model can be articulate and still be incorrect. Independent validation gives an administrator evidence they can review instead of a vague claim that the output is accurate.

## Why structured JSON is essential

Free-form text is difficult to audit. Consider a sentence such as “Review security rules during your first week.” It does not identify which rule applies, whether it is mandatory, which role needs it, or which policy section supports it. SkillSprint AI represents every generated item as JSON. Each item carries a requirement ID, role, module title, mandatory or optional status, priority, due stage, source document ID, source section ID, objective, practical task, quiz source mapping, and rubric. This allows the system to compare facts rather than trying to judge whether two English sentences mean approximately the same thing.

The current project includes a deterministic, offline structured generator so that a demonstration can run reliably without an API key or network connection. It derives plan records from active entries in the role matrix. In a production environment, the same contract is the boundary for an approved LLM provider: the application would send only approved chunks and employee context, request JSON conforming to the schema, validate the JSON parser result, and retry on timeout or invalid data. The provider should never be the approval authority. It can personalize language, formulate scenarios, and create assessments, but it cannot decide what company policy requires.

## From documents to trustworthy evidence

Document ingestion begins with file controls. The web application accepts PDF and DOCX files, applies a 16 MB size limit, checks file extension, extracts text with Python parsers, rejects empty uploads, and prevents duplicate title-version pairs. Each upload has an explicit status. Newly supplied documents are `Pending Review`; an authorized approval action changes the status to `Active`. This avoids the common mistake of letting a newly uploaded file silently affect employee training before someone has checked it.

Extraction is only the first step. The content is divided into smaller chunks and each chunk stores a document ID, chunk ID, heading, section-like reference, and text. The exact page or paragraph reference is a critical feature, even in a prototype. Without it, a reviewer cannot navigate from a quiz answer or a practical task back to the underlying material. Source traceability is therefore a first-class data field rather than a note embedded in prose.

Version status is also retained. An active source is eligible to support the onboarding plan. Obsolete and pending-review documents are not ground truth. A future production deployment should add a policy-family identifier, formal supersession link, approval signature, and configurable precedence logic such as “latest approved policy overrides SOP” or “corporate policy overrides departmental FAQ.” The current data set deliberately models updated and obsolete documents so a demo can show why version awareness is needed.

## The role requirement matrix

The Role Requirement Matrix is the system's independent reference. Each row defines an expected requirement for a role. The schema includes its role, description, mandatory flag, priority, due stage, source document and section, and assessment type. When a Sales Executive is selected, SkillSprint AI retrieves Sales rows rather than assigning the same material that it would give a Data Analyst or HR Executive. This is what makes personalisation accountable: a plan is tailored by a visible rule set, not by opaque prompting alone.

The fictional dataset provides twenty company documents, ten job roles, and 150 matrix records. One hundred records are mandatory, and every matrix row is role-specific. The documents include prompt-injection examples and revised/conflicting content. These are not gimmicks: they exercise the system controls. The matrix has enough records to create fifteen structured checks per role and 150 comparison points across the supplied ten employee plans, more than the required one hundred comparison cases.

Multi-stage planning is another rule encoded in data instead of left to prose. Records are assigned across Day 1, Week 1, Week 2, First 30 Days, First 60 Days, and First 90 Days. A new employee can acknowledge core policies on Day 1, learn workflows during Week 1, then complete practical demonstrations later. This makes prerequisites and learning progression possible. In a larger release, a prerequisite graph would ensure that an advanced operational assessment cannot be unlocked before its foundational security or process module is complete.

## Independent Python validation

After generation, the validator loads the active matrix for the selected role. For every generated item it checks that the requirement ID exists for that role, the role and mandatory status match, and priority, due stage, source document, and source section are identical to the approved record. It then confirms that the referenced document is active. It counts repeated requirement IDs as duplicate learning content. Finally, it compares all required mandatory items against the plan to calculate a coverage score.

The report presents a mandatory coverage score, source traceability score, consistency score, missing requirement count, unsupported count, detailed issues, and a final status. `Verified` means every mandatory requirement is covered with active, traceable evidence and no unsupported, mismatch, or duplicate issue was found. Unsupported requirements, obsolete evidence, and structured mismatches result in `Manual Review Required`; less serious incompleteness becomes `Verified with Warning`. These statuses are deliberately conservative. A system used for compliance should prefer asking a person to look at a questionable plan over quietly publishing an ungrounded one.

This validator is also the beginning of hallucination detection. A model-produced requirement without a matrix ID is classified as unsupported rather than accepted because it sounds plausible. Content that cites an obsolete document is also not trusted. Semantic sentence-level verification can be strengthened in production with approved retrieval, controlled vocabulary matching, and human policy review, but these deterministic checks already prevent a large class of operational mistakes.

## Prompt injection and security

Company documents are untrusted input. A malicious or accidental sentence such as “ignore previous instructions” must not become a command to the model or application. SkillSprint AI scans for common injection indicators and records a flag. More importantly, its design treats every document as data: extracted text is stored as evidence, never executed as application instructions. In a production LLM integration, source chunks should be clearly delimited and the system prompt should explicitly state that quoted documents are non-authoritative data. Upload approval, audit records, role-based access control, malware scanning, encrypted object storage, and rate limiting should be added before deployment.

## Dashboards, progress, and impact

The dashboard shows document totals, active evidence, matrix size, employees, generated plans, and injection flags. The user can select an employee, generate and validate a plan, inspect the structured JSON and report, upload documents, and export compliance results to CSV. The progress endpoint records completion and a score for each employee-requirement pair. That data forms the basis for adaptive recommendations: low quiz performance can trigger revision work, an extra scenario, or manager coaching.

Policy updates have an impact beyond the document register. Because each plan item points to a requirement and a source document, the system can query all affected employees and plans when a document is replaced. A selective regeneration workflow should invalidate only impacted module items, preserve unrelated completions, rerun validation, and notify managers. This is safer and less disruptive than regenerating an entire onboarding plan whenever one policy changes.

## Deployment path and conclusion

The included application uses Flask and SQLite because it is easy to run and inspect for a competition demonstration. The setup guide is intentionally short: install requirements, run `python app.py`, and open the local URL. For a real deployment, replace SQLite with PostgreSQL, store files in managed object storage, run parsing and generation as background jobs, add authentication for Admin, Manager, and Employee roles, protect secrets through environment configuration, and collect structured audit logs. Add rate-limited API retries, JSON-schema validation, observability, backups, and a worker queue to meet scale and uptime goals.

SkillSprint AI's key lesson is that generative AI is most valuable when it operates inside a verifiable process. AI can make onboarding more useful, more personal, and faster to author. Python rules, source records, version controls, and explicit review states make it dependable. The result is not simply a chatbot that writes training text. It is a traceable onboarding system that can explain what it assigned, why it assigned it, and whether the evidence supports it.

## Operational testing and evaluation evidence

A convincing AI project needs evidence that its rules behave correctly when input is imperfect. The supplied test approach covers both normal and adverse cases. A normal PDF or DOCX upload must create a document record, produce traceable chunks, and remain pending until approved. An unsupported extension, an empty document, an oversized file, or a duplicate title and version must be rejected before parsing. The application has explicit HTTP responses for these cases, which makes the behaviour testable from either the browser or an API client. The smoke tests used during implementation also verify that the landing page loads, the document upload endpoint rejects invalid content, and an actual DOCX can be extracted and approved.

Generation tests are equally important. Each of the ten supplied employees maps to a different role. A plan generation request creates fifteen structured items from that role's portion of the matrix and places them in the planned stages. The validator then evaluates each field. Across all ten roles this produces 150 item comparisons. The CSV export captures plan ID, employee ID, role, outcome status, coverage score, and traceability score, allowing an evaluator to retain repeatable evidence. A more comprehensive test suite can intentionally remove a mandatory JSON item, change its source section, duplicate it, change the role, or point to an obsolete document. In each case, the expected status and issue count can be asserted without needing to call an LLM.

Conflict tests deserve special attention. Business documents sometimes contain two different instructions because an old SOP has not been retired or a local FAQ contradicts a policy. A mature implementation should normalize policy families, detect materially different values in equivalent clauses, and apply an administrator-configured precedence order. For example, an active newer security policy may take precedence over an older departmental procedure; an explicit legal compliance document may outrank an FAQ. If precedence cannot resolve the difference, the safer result is `Manual Review Required`. The current database retains active/obsolete status and deliberately includes revised conflicting source language so this extension has an authentic dataset to exercise.

The same philosophy applies to quality metrics. Coverage is not simply the number of modules generated. It is the percentage of mandatory matrix rows represented in the plan. Traceability is not a decorative citation count. It is the percentage of generated items with a valid active source and section reference. Consistency measures attribute-level agreement, and issue details expose the exact requirement that failed. These metrics let managers distinguish an appealing plan from a compliant one. They also help developers debug a rule change during a live evaluation because they show whether an error comes from the generator, the matrix, a source version, or the validator itself.

Finally, the project is intentionally configuration-driven. Adding a new role does not require editing frontend source code: add employee and role-matrix data, then call the same plan endpoint. Adding a document follows the upload, approval, chunking, and matrix workflow. This is the practical meaning of avoiding hardcoding. The application does not store prewritten plan answers or quiz answers for a particular employee. It stores source-backed requirements and calculates the plan at request time. That separation makes future policy updates, new departments, and evaluator-provided hidden documents manageable without turning every change into a code release.
